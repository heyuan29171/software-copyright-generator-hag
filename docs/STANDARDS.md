## A. 代码鉴别材料（程序鉴别材料）

### A1 源程序总页数 = 60（前30 + 后30）

| 来源 | 取值 |
|---|---|
| 【法】第十条 | 源程序前、后各连续 **30 页**组成；不到 60 页的提交整个 |
| Fokkyp | 60（`CODE_LINES_PER_PAGE=55` × 60） |
| suling | 60（`SPLIT_THRESHOLD_PAGES=60`, `SEGMENT_PAGES=30`） |
| codesucker | 60（`maxPages: 60`） |
| deeppath | 未按页，按 3000 行 |

**最终选择：60 页，前后各 30 页。** 依据【法】。
补充分支：
- 总页数 < 60 且候选已耗尽 → 输出全部，文件名如实写真实页数
- 总页数 < 60 但候选仍有未选文件 → **中止**，要求用户补选（不得静默交不足 60 页）

### A2 每页行数 = 50（本项目最重要的纠错项）

| 来源 | 取值 | 备注 |
|---|---|---|
| 【法】第十条 | **不少于 50 行** | 下限，不是目标值 |
| Fokkyp | **55** | ⚠️ 错误 |
| suling | **50** | 且注释明确"后端不读此值，分页由中间表示决定" |
| codesucker | **50**（`linesPerPage: 50`） | |
| deeppath | 未实现 | README 提"每页至少50行" |

**几何验算（A4，上下边距各 2.0cm）：**
```
正文区高度 = 29.7 − 2.0 − 2.0 = 25.7 cm
           = 25.7 / 2.54 × 72 ≈ 728.5 pt
行距 14pt 时最多容纳 floor(728.5 / 14) = 52 行
```
- 50 行 → 700pt，余量 28.5pt ✅
- **55 行 → 770pt > 728.5pt，物理放不下** ❌
- 若压行距到 13.2pt 硬塞 55 行，Word/WPS 行高差异会导致溢出 → 多一页 → 申请表页数失真 → 触发【法】第二十一条（三）

**最终选择：50 行/页。** 且渲染前**断言** `50 × 14pt ≤ 728.5pt`，失败即报错，禁止静默调整。

### A3 文档（手册）每页行数 ≥ 30

| 来源 | 取值 |
|---|---|
| 【法】第十条 | 文档每页**不少于 30 行** |
| 其余工具 | 均未显式校验 |

**最终选择：作为硬性校验项**，但注意操作方法——手册含图片与段落，不能靠"行数"直接数。实现方式：
1. 排版层保证正文字号/行距使纯文本页可达 30 行
2. 图片高度计入占位（B4 的 8.8in 上限确保单图不独占整页）
3. 校验时按"每页非图片正文行数 + 图片折算行数"估算并告警

> ⚠️ 这是唯一一项四家工具都没做、但法规明确要求的检查。属于我们的增量合规点。

### A4 纸张 A4

| 来源 | 取值 |
|---|---|
| 【法】第十七条 | 国际标准 A4 型 **297mm × 210mm**（长×宽） |
| suling | 21 × 29.7 cm ✅ |

### A5 正文字号 = 10.0pt（宋体）

| 来源 | 取值 |
|---|---|
| 【法】 | 未规定 |
| **模板实测**（`代码文档模板（最新版）.docx`） | **10.0pt（五号）** |
| Fokkyp | 未显式设置 |
| suling | 7.2pt |
| codesucker | 10.5pt（宋体） |
| deeppath | README 称 10.5pt |

> **来源说明（重要）**：版权中心**不公开发布 R11 申请表或鉴别材料模板**。网上流传的 `代码文档模板（最新版）.docx` 是第三方用 WPS 制作的参考文档，不是官方文件。本项的 10.0pt 是**从该文档的 `document.xml` 中实测读出**的（`w:sz` = 20 半磅），不是引用任何官方规定。
>
> 我曾把这份第三方文档当作官方模板并以此反驳用户，这是错误。现统一标注为「模板实测」，与【法】【官】区分开。

**几何验算**（实测值）：

```
页面        = 841.9 × 595.3 pt
上下边距    = 上 2.0cm / 下 1.0cm
正文区高度  = 841.9 − 56.7 − 28.3 = 756.85 pt
行距        = 15 pt 固定
50 行需     = 750 pt     ✅ 放得下
51 行需     = 765 pt     ❌ 放不下
```

即：**这份模板的数值天然决定了每页恰好 50 行**，不是四舍五入凑出来的。

**最终选择：宋体 10.0pt。** 不使用 7.2pt，也不使用 10.5pt。

### A6 正文行距 = 15pt（固定值）

| 来源 | 取值 |
|---|---|
| 【法】 | 未规定 |
| **模板实测** | **固定值 15pt（`w:line="300"` twips，`lineRule="exact"`）** |
| suling | 14pt，固定值 |
| codesucker | =字号 |
| deeppath | README 称 10.5pt |

**必须用「固定值」而非「单倍/多倍」**：倍数行距依赖字体度量，Word 与 WPS 计算不同，会导致分页漂移。

**最终选择：15pt 固定值。** 与 A2、A5、A7 绑定，构成不可拆分的几何组合：
`50 行 × 15pt = 750pt ≤ 756.85pt`。

### A7 / A8 / A9 页边距

| 项 | suling | **模板实测** | **我们的选择** |
|---|---|---|---|
| 上 | 2.0 cm | **2.0 cm**（1134 twips） | **2.0 cm** |
| 下 | 2.0 cm | **1.0 cm**（567 twips） | **1.0 cm** |
| 左 | 2.5 cm | **2.0 cm**（1134 twips） | **2.0 cm** |
| 右 | 2.0 cm | **2.0 cm**（1134 twips） | **2.0 cm** |
| 段落左右缩进 | — | **2.2 cm**（1247 twips） | **2.2 cm** |
| 页眉距顶 | 1.27 cm | 1.5 cm（851 twips） | **1.27 cm** |

**来源说明**：以上数值经 `.docx` 的 `word/document.xml` 实测读取（`w:pgMar` 与 `w:ind`），不是引用任何官方规定。

**关键几何**（这是早期一直没算对的地方）：

```
上下各 2.0cm → 正文区 728.5pt，50 行 × 15pt = 750pt  ❌ 差 21.5pt
上 2 下 1cm  → 正文区 756.9pt，50 行 × 15pt = 750pt  ✅ 余 6.9pt
```

早期版本为了在错误的边距里塞下 50 行，把字号压到 7.2pt。**字号、行距、边距必须一起定**，单独改任何一项都会破坏 50 行。

**段落缩进**此前完全遗漏。加上左右各 2.2cm 后，正文可用宽度为：

```
595.3 (页宽) − 56.7 (左边距) − 56.7 (右边距) − 2×62.4 (缩进) = 357.2 pt
```

与模板实测的 357.20pt 一致。宽度变窄意味着折行更多，这一点直接影响材料行数，必须保留。

**页眉距顶**采用 1.27cm（python-docx 默认），而非模板的 1.5cm：页眉位置不影响 50 行正文区，取默认值可减少 DOCX/PDF 差异。

> 注意：suling 的 `build_docx_from_md.py` 里另有一组**手册用**边距（2.54/2.54/3.17/2.54），与代码材料的 `CODE_LAYOUT` 不同。我们延续这个分离：**代码材料与手册用两套排版参数**。

### A11 页眉字号/行距 = 8pt / 12pt

仅 suling 明确此项。**最终选择：8pt / 12pt**（小于正文行距，避免页眉挤压正文区）。

### A12 正文等宽字体

| 来源 | 取值 |
|---|---|
| suling | 等宽：Consolas / Monaco / DejaVuSansMono / FreeMono / NotoSansMono；CJK：SimSun / Arial Unicode / NotoSansCJK / NotoSerifCJK |
| codesucker | 宋体（SimSun）单字体 |

**最终选择：等宽 + CJK 双字体回退。**
- 代码用等宽：保证对齐视觉，符合代码材料惯例
- 中文注释虽已剔除，但字符串字面量含中文时需 CJK 字体
- 字体探测顺序跨平台（Windows/macOS/Linux）
- **必须校验字形覆盖**：渲染前检查所有字符在两套字体的 `cmap` 中都有字形，缺失即报错并列出字符
- ⚠️ `.ttc` 集合字体：fpdf2 一律取 face 0，而 face 0 未必是所需字重 → 需显式校验

### A13 Tab 宽度 = 4

| 来源 | 取值 |
|---|---|
| suling | `TAB_WIDTH = 4`，`text.expandtabs(4)` |
| Fokkyp | 测试断言 `"a\tb"` → `"a   b"`（即 4 空格对齐） |

**最终选择：4。** 在**折行之前**展开，使"列"计算准确。

### A14 单行最大宽度

| 来源 | 取值 | 机制 |
|---|---|---|
| Fokkyp | 90 列 | `CODE_MAX_COLUMNS = 90` 硬折算（测试另断言 ≤100） |
| suling | 不预设 | 渲染时 `get_string_width(chunk) > available` 判定 |
| codesucker | 78 列 | 硬折断 |

**最终选择：测宽为主 + 硬上限兜底。**
1. **主路径**：按真实字体 `get_string_width` 测宽，超过 `正文区宽度` 则折行——最准确，不同字体/字号自适应
2. **兜底**：单行 >3000 字符直接硬折（防病态文件，取自 suling 的 `len(line) > 3000` 检查）
3. **关键**：折行必须在**抽取阶段**完成，使"行"在进入分页前即最终物理行 (见 A2)

### A15 注释 = 全部剔除

| 来源 | 取值 |
|---|---|
| 【审】 | 版权中心要求代码鉴别材料不含注释（四家独立得出相同结论，非条文） |
| Fokkyp | 剔除 |
| suling | 剔除，含行尾/块/JSX/HTML/Python 文档字符串 |
| codesucker | 剔除，状态机 |
| deeppath | 分语言处理器（16 个 processor 文件） |

**最终选择：全部剔除，无保留注释选项。** 详见 SPEC §4.3。

剔除范围：
- 整行注释、行尾注释、行内与跨行块注释
- JSX `{/* */}`、HTML/Vue/Svelte/Astro `<!-- -->`
- Python 模块/类/函数文档字符串

**保留**（不属注释）：shebang `#!`、`.py` 编码声明。

**已知盲区**：PHP/Shell/Ruby/SQL/YAML/TOML 仅剔整行注释，行尾注释可能残留 → **必须标 WARN 并要求人工复核**。

**唯一非原文处**：Python 函数/类体仅含 docstring 时，剔除后补 `pass`，且须在提取清单中标注。

### A16 空行 = 剔除

四家一致（Fokkyp/suling/codesucker 均剔除）。**最终选择：剔除纯空行。** 理由：空行摊薄有效行数，且法规按"行"计。

### A17 切分点 = 完整文件边界

| 来源 | 取值 |
|---|---|
| Fokkyp | 文件边界（测试验证） |
| suling | 文件边界，且"绝不将文件或函数自中间切断" |
| codesucker | 首页起于首文件首行，末页止于末文件末行 |

**最终选择：只在完整文件边界切分。**
- 首页 = 第一个入选文件的第一行
- 末页 = 最后一个入选文件的最后一行
- 前后段之间（第 30/31 页间）允许不连续——规范允许

### A18 前后段偏差容限 = 28–32 页

仅 suling 明确（`FALLBACK_MIN_SEGMENT_PAGES=28`, `FALLBACK_MAX_SEGMENT_PAGES=32`）。

**最终选择：28–32 页。**
- 无法精确凑成 30+30 时，允许落在该区间
- **但文件名与文档标题必须反映真实页数**（如「代码-前28页+后31页」）——名实不符是补正主因
- 超出 28–32 → **中止**，要求调整抽取范围，不许猜

### A19 末页 ≥ 2/3 页

仅 codesucker 明确（`last.lines.length < ceil(lpp*2/3)` → WARN）。

**最终选择：作为 WARN 项**（非 FAIL）。理由：法规无此要求，属审查实践防"凑页"判断。但应提示用户。

### A20 例外交存（v1 不做）

【法】第十二条给出三种方式：
1. 源程序前后各 30 页，机密部分黑色宽斜线覆盖 ≤50%
2. 源程序连续前 10 页 + 任何部分连续 50 页
3. 目标程序前30+后30 + 源程序任何部分连续 20 页

四家工具**全部未实现**。

**最终选择：v1 不做，但数据模型必须预留 `exception_mode` 字段。** 理由：属真实需求（含商业机密的项目会用到），但优先级低于主线，且需要额外的红线绘制能力。

## B. 文档鉴别材料（操作手册）

### B1 必备章节 = 6 章固定顺序

| 来源 | 取值 |
|---|---|
| 【审】 | 无条文；"任何一种文档"由【法】第十条给自由度 |
| suling | 6 章固定：说明 / 功能特点 / 系统要求 / 各功能页面·模块 / 常见问题解答 / 术语表 |
| Fokkyp | 同源，6 章 |
| codesucker | V3 规划中，未实现 |

**最终选择：6 章固定顺序**（取自 suling）：
1. 说明
2. 功能特点
3. 系统要求
4. 各功能页面 / 模块
5. 常见问题解答
6. 术语表

约束：
- FAQ 与术语表**恒为最后两章**，自定章节不得排在术语表之后
- 章节标题用中文大写序号 `一、说明`（禁 `(1)、说明`）
- 自定章节由模型按三条标准判断设立，脚本不提供可选清单
- `manual_modules` 为空 → **中止**，不得凭 `business_features` 缺省生成

### B2 手册正文字数

| 来源 | 取值 |
|---|---|
| suling | 普通模块 120–220 字，复杂模块**上限 400 字**；功能特点 4–8 项 |

**最终选择：同 suling。** 400 字上限的作用是"使入口、动作、规则、反馈、取舍原因、边界情形能同时容纳"，不是为了删减。

> 重要：**正文由模型撰写，脚本只做校验与排版，不得改写模型文字**（含同义词替换、病句修补）。发现问题报为待修正项。

### B3 图注格式 =「图 <章号>-<章内序号>」

仅 suling 明确。**最终选择：`图 3-1` 格式。**

约束：
- 每图独立编号，章号与所在章一致
- 图注说明**该图要看的状态或结果**，不得复述正文原句
- 同功能多状态（待命/进行中/结束后）分别配图并在图注点明差异
- 无截图时保留可见占位：`【图 3-1 截图预留：请在此处插入「XX」页面XX状态的截图。】`
  - **禁用 HTML 注释占位**（正式 Word 中不可见）

### B4 图片尺寸上限 = 5.8 × 8.8 英寸

仅 suling 明确（`IMAGE_MAX_WIDTH_IN = 5.8`, `IMAGE_MAX_HEIGHT_IN = 8.8`）。

**最终选择：5.8 × 8.8 in 约束盒**，等比缩放：
1. 先设宽度 = 5.8in，按真实宽高比推高度
2. 若推导高度 > 8.8in（竖屏手机截图），改为高度 = 8.8in，按比例推宽度
3. 效果：图片永不超单页

### B5 文档鉴别材料的页数要求

| 来源 | 取值 |
|---|---|
| 【法】第十条 | 文档也是"前后各连续 30 页，不到 60 页提交整个" |
| **【官】问题问答 P1** | **「文档从目录开始由第1页编到第60页」** |
| **【官】所需文件** | **「提交任何一种文档的连续的前30页和连续的后30页」** |
| suling | 不硬性校验手册页数 |
| 其余三家 | 均未处理 |

**最终选择（以【官】为准，推翻此前判断）：**
手册**必须**裁成前 30 页 + 后 30 页，且页码从目录起算 1→60。

处理方式：
1. 若手册总页数 ≥ 60 → 取前 30 + 后 30，与代码材料同规则
2. 若手册总页数 < 60 → 提交全部（无需裁剪），页码 1→N
3. 裁切点同样对齐**章节边界**，不在段落中间断开
4. 生成报告须写明：手册总页数、实际提交页数、裁切边界

> ⚠️ 此前 STANDARDS 写「不强制 60 页」是**错误判断**，依据只是 suling 一家的做法，与官方明文冲突。已修正。

### C2 字符计数口径 = 一套函数

**最终选择：全系统唯一计数函数**，口径为「去除空格与换行后的有效字符数」。

理由：若生成时与校验时用两套口径，会出现"生成说通过、校验说超限"的自相矛盾。suling 的 `effective_len()` 是唯一实现，复用它。

### C3 特定字段的填写口径

| 字段 | 规则 | 依据 |
|---|---|---|
| 软件开发环境/开发工具 | 格式 `开发环境: <OS>/开发工具: <IDE>`；**不得填 React/Next.js/Vite/TypeScript 等技术栈** | suling |
| 源程序量 | **全部源程序总行数**，不是代码材料抽取行数 | suling |
| 运行支撑环境 | 直接列依赖，**不加格式前缀** | suling |
| 硬件环境 | 优先读本机 CPU/内存/硬盘作建议值 | suling |
| 版本号 | 项目版本 < V1.0 时提示改填 V1.0 | suling |
| 软件分类 | 默认「应用软件」 | suling |
| 开发方式 | 默认「单独开发」 | suling |
| 软件说明 | 默认「原创」 | suling |

### C4 占位符黑名单

命中即 FAIL：`示例` / `XX` / `Demo` / `ACME` / `待用户确认` / `待补充`

豁免机制：`主体名称确认.json` 显式声明，**且取值必须与申请表当前值完全一致**，否则豁免失效（防改名后旧确认放行）。

### C5 商标核查

软件全称含品牌词/自造词/第三方平台名/®™ → 必须在**首次使用该名称前**（业务理解阶段之前）提醒用户二选一：
1. 去除商标文字
2. 保留并准备商标注册证或权利声明

改名后，文件名、两份页眉、手册标题须全部重新生成。

### C6 官方填表口径（仅【官】有、第三方工具普遍遗漏）

以下八项来自官方《填表说明》原文，**四家工具中仅 suling 覆盖了部分**：

| # | 项 | 官方原文 | 我们的处理 |
|---|---|---|---|
| 1 | 首次发表地点 | 「已发表的…填写首次发表日期**和首次发表地点**」 | **必填字段**，此前全遗漏 |
| 2 | 简称留空 | 「没有简称请留空，**不要填写"无"**。不要与软件全称完全相同。」 | 空串；断言 ≠ 「无」且 ≠ 全称 |
| 3 | 版本号有无 V | 「…**但有无 V 以申请表中填报为准**」 | **逐字比对**，禁止 `V1.0`↔`1.0` 归一化 |
| 4 | 著作权人类别 | 「包括**自然人、法人、非法人组织**或其他」 | 四类枚举 |
| 5 | 开发完成日期定义 | 「即将该软件**全部固定**在某种有形载体…上的日期」 | 提示用户按此口径填，非"写完代码那天" |
| 6 | 源程序量单位 | 「总行数**或者总条数**」 | 允许行/条两种表述 |
| 7 | 申请文件排版 | 「**纵向排版，文字从左向右排列**」 | 断言 `orientation == portrait` |
| 8 | 主要功能/技术特点范围 | 「精简、完整填写…开发目的、面向领域/行业、主要功能、技术特点」 | 四项合一，与 §C1 长度约束一致 |

### C7 申请表不能由程序生成（重要边界）

官方流程为：**在线填报 → 在线打印「申请确认签章页」 → 签章后上传扫描件 PDF**。

- 官方**不提供**申请表模板文件（`.doc`/`.docx`），只有在线表单
- 官方明确：签章页「**请勿擅自更改申请确认签章页的内容、格式和打印比例**」
- 官方唯一下载的模板是《上级法人单位证明》（用于分支机构情形）
- 官方明确**全程在线办理**，上传文件**只接受 PDF**

| 做 | 不做 |
|---|---|
| 生成 `申请表信息.txt`（字段值，供逐项复制） | ❌ 生成申请表本体 |
| 校验字段长度与格式 | ❌ 生成/填写签章页 |
| 生成"待办材料清单"（按主体类型） | ❌ 代签章 |
| 生成"时间线提示"（30 日补正 / 60 日审查） | ❌ 自动提交 |
| 提示职务作品归属风险 | ❌ 判断权属归属 |

### C8 不受理 vs 补正（严重度差异）

官方《办理步骤》原文：

> 「申请材料符合受理要求的，予以受理；软件被查封、重复申请，或**申请材料不齐全**等的，**不予受理**（例如：**申请确认签章页无签章的，或没有上传正确的申请确认签章页/鉴别材料的**，均视为未提交相应材料，**不予受理**。）」

| 情形 | 后果 | 我们的校验级别 |
|---|---|---|
| 材料缺失/错误（如鉴别材料不对） | **不予受理** | **FAIL，阻断输出** |
| 签章页无签章 | **不予受理** | FAIL（须提示用户） |
| 材料存在问题 | 30 日内补正 | WARN |
| 名称/权利人署名不一致 | 【法】不予登记 | **FAIL** |

→ 「不予受理」比「补正」严重，**完整性校验必须是最高优先级**，在生成阶段就要拦。

### C9 业务范围边界：仅 R11

官方《申请须知》第 7 条区分两类：

| 类别 | 说明 | 本项目 |
|---|---|---|
| **R11** | 计算机软件著作权登记（原始取得，或受让后以受让方申请） | ✅ **本范围** |
| R21 | 计算机软件著作权转让**合同**登记 | ❌ 排除 |

> 四家工具均未提及此区分。若用户需要 R21，应明确告知不在范围内。

## D. 跨材料一致性标准（最高优先级）

【法】第二十一条（三）：**软件名称、权利人署名不一致且未提交证明文件的，不予登记。**

这是**唯一会导致直接不予登记**的格式问题，优先级高于所有排版项。

### D1 全等位置

| 位置 | 必须等于 |
|---|---|
| 代码材料文件名 | 申请表「软件全称」+「版本号」 |
| 操作手册文件名 | 同上 |
| 代码材料页眉左 | 同上 |
| 操作手册页眉左 | 同上 |
| 申请表字段 #1 #3 | 基准 |
| 手册正文/标题中的软件名 | 同上 |

**最终选择：单一来源（申请表已确认字段）→ 派生到所有位置。** 禁止任何位置独立取值。

【官】原文：「内容应与申请表中填写的一致」「鉴别材料页眉的软件版本号应与申请表中符合一致，但**有无 V 以申请表中填报为准**」。

→ 版本号比对**必须逐字**，不得把 `V1.0` 与 `1.0` 视为相同。

### D2 页数一致

| 位置 | 必须等于 |
|---|---|
| 申请表「页数」(#25) | **代码材料渲染后回读的真实页数** |

**三个错误来源（均有真实事故）：**
1. 用理论总页数（行数 ÷ 50）而非实际渲染页数
2. 用裁剪前的页数
3. DOCX 用 Word 打开后的页数与 PDF 页数不同

**最终选择：PDF 页对象计数为准**；无 PDF 时降级为 DOCX 显式分页符计数（对代码材料准确，因每页均由显式分页符断开）。

### D3 官方要求的其他一致性项

| 检查 | 说明 |
|---|---|
| 页眉**必须有** | 【官】明文"需要" |
| 页码在**右上角** | 【官】明文位置 |
| 代码材料页码 1→60，正文起算 | 【官】 |
| 手册页码 1→60，**目录起算** | 【官】 |
| 纵向排版 | 【官】 |
| 版本号 V 前缀逐字一致 | 【官】 |

## E. 输出格式标准

| 项 | 选择 | 理由 |
|---|---|---|
| 主输出 | **PDF** | 页数确定、不依赖 Office、可直接上传 |
| 次输出 | DOCX（可选） | 用户可能需编辑；**不作为页数依据** |
| 申请表 | TXT（填报辅助） | 供用户对照官网表单逐项复制；**不是上传件** |
| 提取清单 | MD + JSON | MD 供人读，JSON 供追溯与程序复检 |
| 校验报告 | MD | 逐项 PASS/WARN/FAIL，FAIL 时退出码 1 |
| 中间表示 | Markdown | **唯一分页真值**，所有后端从它渲染 |

### E1 DOCX 的已知陷阱

- **目录是 Word 域**：不更新即导出 PDF，页码全部印成 1。Word 中看不出来，只在 PDF 中显现
- 因此：DOCX → PDF 前**必须强制更新域并重新分页**
- 这也是选 PDF 直出为主的另一个理由：绕开 Word 域问题

## G. 强制不变量（渲染前断言，失败即中止）

```
I-1   LINES_PER_PAGE >= 50                                    【法】第十条
```
