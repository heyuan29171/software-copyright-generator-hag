## 1. 法规依据（唯一权威源）

**《计算机软件著作权登记办法》**（2002 年 2 月 20 日国家版权局 1 号令公布，自 2002 年 2 月 20 日施行）
- 官方发布页：https://www.ncac.gov.cn/xxfb/flfg/bmgz/202410/P020241015604759788122.pdf
- 本文所有 `【法条】` 标注均引自该 PDF 原文（已逐条核对，见附录 A）

### 1.1 硬性条款

| 编号 | 法条 | 原文要点 | 对本项目的要求 |
| --- | --- | --- | --- |
| R-01 | 第十条 | 程序和文档鉴别材料由源程序和**任何一种**文档的**前、后各连续 30 页**组成 | 60 页分两段，各 30 页 |
| R-02 | 第十条 | 整个程序或文档**不到 60 页**的，提交整个 | 不足则全量输出，不得拼凑 |
| R-03 | 第十条 | 除特定情况外，**程序每页不少于 50 行** | **行数下限 = 50**，不可用 55 |
| R-04 | 第十条 | 除特定情况外，**文档每页不少于 30 行** | 手册排版下限 30 行/页 |
| R-05 | 第十二条 | 例外交存三种方式（覆盖 ≤50% / 前10+任意50 / 目标30+30+源码20） | v1 不做，但数据模型须预留 |
| R-06 | 第十七条 | 文件须用 **A4 型 297mm×210mm** 纸张 | 页面尺寸固定 |
| R-07 | 第十七条 | 申请表须用**中文**填写；外文证件须附中文译本 | 输出语言约束 |
| R-08 | 第二十一条（三） | 申请文件中**软件名称、权利人署名不一致且未提交证明文件**的，**不予登记** | **一致性校验为最高优先级** |
| R-09 | 第二十一条（一） | 表格内容填写不完整、不规范且未在指定期限内补正 | 字段完整性、长度限制必须校验 |
| R-10 | 第二十二条 | 补正期限 30 日 | 校验报告须提示补正风险 |
| R-11 | 第二十条 | 受理日起 60 日内审查完成 | 仅作背景信息 |

### 1.2 非硬性但行业通行口径（来自官方审查实践，非条文）

以下**不是**法条，是社区实践总结（`suling-fun` 与 `codesucker` 独立得出相同结论），作为默认值而非硬约束：

- 代码材料剔除**全部注释**（含行尾注释、块注释、JSX/HTML 注释、Python 文档字符串）
- 代码材料剔除**纯空行**
- 页眉包含软件全称 + 版本号（右侧页码）
- 末页不少于整页的 2/3（避免被认定凑页）
- 切分点对齐**完整文件边界**，不在函数中间截断

> ⚠️ 这些是默认策略，必须可配置、可在校验报告中说明，不能硬编码为"法条规定"。

### 2.3 ⚠️ 分歧点一：每页行数 50 vs 55

**这是本规格最重要的纠错项。**

- `F` 用 `CODE_LINES_PER_PAGE = 55`
- `S` 用 `LINES_PER_PAGE = 50`，且注释明确写道：*"每页行数不在此处：两个后端都不读取该值，分页一律由抽取环节产出的中间 Markdown 决定"*
- `C` 用 `linesPerPage: 50`

**几何验算**（A4 29.7cm，边距取自流传模板实测：上 2.0cm / 下 1.0cm）：

```
正文区高度 = 29.7 − 2.0 − 1.0 = 26.7 cm
          = 26.7 / 2.54 × 72 ≈ 756.9 pt
可容纳行数 = floor(756.9 / 15) = 50 行
```

- 用 **50 行**：占用 750pt，余量 6.9pt ✅ 刚好放下
- 用 **55 行**：需 55 × 15 = 825pt **> 756.9pt，物理上放不下** ❌
- 若沿用上下各 2.0cm 的边距：正文区 728.5pt，50 行 × 15pt = 750pt **同样放不下**

这解释了为什么字号、行距、边距三者必须一起定：「上 2 下 1 + 宋体 10pt + 固定 15pt」是一组相互咬合的数值，单独改动任何一项都会破坏 50 行。

即使把行距压到 13.7pt 以塞进 55 行，也会因 WPS 与 Word 的行高/字体回退差异导致溢出，表现为：多出第 56 行、或多出一整页 → 申请表「页数」与实际不符 → 命中 R-08 / R-09 的退回条件。

**结论：行数固定 50，字号 10.0pt（宋体），行距 15pt 固定值，边距上 2.0 / 下 1.0 / 左右 2.0 cm，段落左右缩进 2.2 cm。** 渲染前必须断言 `max_lines × BODY_LINE_PT ≤ 正文区高度`，不满足即报错，禁止静默调整。

### 2.4 分歧点二：单行超长如何处理

- `F`：硬截断到 90 列（`CODE_MAX_COLUMNS = 90`），测试断言"所有行 ≤ 100 列"
- `S`：不预设列数，改为**渲染时测宽**：`if _line_width(...) > available:` 则处理溢出（`render_code_pdf.py:433`）
- `C`：按 78 列硬折断

**本项目取值**：采用 `S` 的测宽方案为主（真实字体宽度才是最准的），但**必须**保留 `F` 的字符兜底上限（≥3000 字符的行先硬折，防止病态文件）。

**关键**：无论哪条路径，**折行后总行数会变化，必须在抽取阶段就完成折行**，使"行"在进入分页前即为最终物理行。`F` 的测试正好验证了这一点（`test_material_lines_drop_blanks_and_wrap`）。

### 2.5 分歧点三：分页的真值来自哪里

- `S`：中间 Markdown 是**唯一真值**，DOCX 与 PDF 两个后端都读它，逐页必须一致（`common.py:35-42` 注释）
- `C`：渲染时用 `pageBreakBefore` 显式分页，不靠排版凑页
- `D`：无

**本项目取值**：中间表示（IR）→ 渲染后端。**所有后端必须从同一 IR 渲染**，且渲染后回读实际页数。

```
I-6  每页实际行数 >= 50（末页除外）               # R-03
```

## 4. 代码材料流水线

```
discover → filter → clean → select → wrap → paginate → render → audit
```

### 4.1 各阶段契约

| 阶段 | 输入 | 输出 | 关键约束 |
| --- | --- | --- | --- |
| `discover` | 项目根目录 | 文件清单（含编码、大小、二进制标记） | 按**内容**识别源码，不靠扩展名白名单 |
| `filter` | 文件清单 | 候选清单 | 排除 `node_modules/dist/build/.next/.nuxt/coverage/target/vendor`、lock 文件、图片字体二进制、sourcemap/minified、自动生成文件 |
| `clean` | 候选源码 | 去注释、去空行后的行 | **逐字符状态机**，不用正则（字符串内 `//`、`#`、`/*` 不得误删） |
| `select` | 候选 + 用户选择 | 选中文件集 | 必须经用户确认；脚本不得自动全选 |
| `wrap` | 代码行 | 折行后的物理行 | Tab 展开为 4；超宽按测宽折行 |
| `paginate` | 物理行 | 页 | 每 50 行一页；显式分页，不靠排版 |
| `render` | 页 + 页眉信息 | PDF（主）/ DOCX（次） | 从**同一 IR** 渲染；渲染后回读页数 |
| `audit` | 渲染结果 | 审计项列表 | 见 §4.4 |

### 4.2 前后段切分算法

```
if total_pages < 60:
    if 候选已全部选中: 输出「代码-全部」
    else:              中止，要求用户补选   ← 不得静默接受不足
else:
    尝试重排已选文件的顺序，使前段恰 30 页、后段恰 30 页
    if 成功:            输出「代码-前30页+后30页」
    elif 前后各落在 28–32 页: 输出并在文件名/标题如实反映真实页数
    else:               中止，要求调整选择范围        ← 偏差过大不猜
```

**硬约束**：切分点**只落在完整文件边界**。选中大文件过多时对齐余地会变窄，应在选择阶段就提示用户补选小文件。

### 4.3 注释剔除规格

| 语言 | 方法 | 覆盖 | 已知盲区 |
| --- | --- | --- | --- |
| Python | 标准库 `tokenize` + `ast` | 模块/类/函数 docstring | docstring 独占函数体时用 `pass` 补位（材料中唯一非原文处） |
| JS/TS/Java/C/C++/C#/Go/Rust/Swift/Kotlin/Dart/CSS/SCSS | 逐字符状态机 | JSX `{/* */}`、模板注释 | — |
| HTML/Vue/Svelte/Astro | — | `<!-- -->` | — |
| PHP/Shell/Ruby/SQL/YAML/TOML | 仅整行注释 | — | **行尾注释可能残留**，须标为 WARN 并人工复核 |

**保留项**（不是注释）：
- 文件首行 shebang `#!`
- `.py` 第一/二行的编码声明 `# -*- coding: ... -*-`

**校验**：`verify` 阶段复用**同一剔除函数**复检，残留即 FAIL。注意——复用同一函数意味着**无法发现函数自身的误判**，误判必须靠人工/独立 agent 核实。

### 4.4 审计项（audit）

参考 `C` 的 `audit.ts`，每项输出 `pass / warn / fail`：

| # | 检查 | 级别 |
| --- | --- | --- |
| 1 | 软件全称非空 | fail |
| 2 | 全称含版本号（如 V1.0） | warn |
| 3 | 存在可用代码内容（>0 行） | fail |
| 4 | 除末页外每页 ≥ 50 行 | fail |
| 5 | 末页 ≥ 2/3 页 | warn |
| 6 | 首页为模块开头、末页为模块结尾 | pass（信息） |
| 7 | 无空行残留 | warn |
| 8 | 无他人署名（`@author`/`Copyright` 与著作权人不符） | **fail** |
| 9 | 文件修改时间不早于成立日期 | warn |
| 10 | **注释残留**（复用剔除函数） | fail（部分语言降 warn） |
| 11 | **实际页数 == 申请表页数** | **fail** |
| 12 | **名称/版本四处一致** | **fail** |

## 5. 文档材料（操作手册）规格

### 5.1 必备章节（固定顺序，不得增删改序）

| # | 章节 | 内容要求 |
| --- | --- | --- |
| 1 | 说明 | 软件定位、目标用户、业务场景、整体流程 |
| 2 | 功能特点 | 4–8 项，每项说明业务作用与用户可见结果 |
| 3 | 系统要求 | 表格：最低配置 / 推荐配置 |
| 4 | 各功能页面 / 模块 | 按真实页面或核心流程逐章；普通模块 120–220 字，复杂上限 400 字 |
| 5 | 常见问题解答 | 3–5 个真实问题 |
| 6 | 术语表 | 软件名、核心业务对象、页面模块术语 |

- `FAQ` 与 `术语表` **恒为最后两章**
- 自定章节不得排在术语表之后
- 章节标题用中文大写序号：`一、说明`（不得用 `(1)、说明`）
- `manual_modules` 为空时**中止**，不得凭 `business_features` 缺省生成

### 5.2 正文由模型撰写，脚本不造句

这是 `S` 反复强调的核心原则，**在 MCP 实现中极易退化**：

- **模型负责**：全部叙述性正文，写成成文段落
- **脚本负责**：章节编号、图注编号、表格渲染、页眉、字数校验、套话检测
- 脚本**不得**改写模型文字（含同义词替换、病句修补）；发现问题报为待修正项

### 5.3 写作硬规则

- 正文不得用 `-`、`*`、`1. 2. 3.` 罗列（表格不受限）
- 不得输出「进入方式：」「操作步骤：」「操作结果与反馈：」类模板小标题
- 禁止「旨在、赋能、一站式、智能化、高效便捷、显著提升、强大能力、丰富功能」等口号
- 功能章节须写明**边界与异常状态**（数据缺失显示什么、前置条件不满足时哪些可用）
- 「原因在于……」式说明必须来自项目真实约束；**判定法：把软件名换成任意其他软件后仍成立 → 是空话，删掉**

### 5.4 图注

- 编号格式：`图 <章号>-<章内序号>`，如 `图 3-1`
- 每图下方一句图注，说明**该图要看的状态或结果**，不得复述正文
- 同功能多状态（待命/进行中/结束后）分别配图并在图注点明差异
- 未取得截图时保留可见占位：`【图 3-1 截图预留：请在此处插入「项目管理」页面列表状态的截图。】`
  - **不得**用 HTML 注释占位（正式 Word 中不可见）

### 5.5 页眉

必须与代码材料页眉**完全一致**：左侧「软件全称 版本号」，**右上角**「页码」。

> ⚠️ **官方原文（问题问答 P1）**：「页眉建议标注该软件名称、版本号，内容应与申请表中填写的一致；**右上角标注页码**，源程序从正文第1页编到第60页，**文档从目录开始由第1页编到第60页**。」
>
> 据此修正：
> - 页码位置 = **右上角**（不是右侧任意位置）
> - 页码纯数字 `1..60`，**不加「第/页」字样**（官方表述为"编到第60页"，未要求包裹格式）
> - **手册页码从目录起算为第 1 页**，不是从正文起算

### 5.6 文档行数下限

R-04 要求文档每页 ≥ 30 行。操作手册因含图片与段落，需在排版层保证：正文段落的行高之和不得使某页低于 30 行——实践中靠合理分页与图片尺寸约束达成，须在校验中检查。

## 6. 申请表字段规格（25 项）

按官网表单顺序。**长度限制必须在生成时校验，`verify` 时复检。**

| # | 字段 | 约束 | 口径 |
| --- | --- | --- | --- |
| 1 | 软件全称 | 必填，须用户显式确认 | 四处一致的唯一来源 |
| 2 | 软件简称 | 可选 | 有常用简称时填 |
| 3 | 版本号 | 必填，显式确认 | 项目版本 < V1.0 时提示改填 V1.0 |
| 4 | 软件分类 | 枚举：应用软件/嵌入式/中间件/系统软件/其他 | 默认「应用软件」 |
| 5 | 开发完成日期 | `YYYY-MM-DD` | — |

### 6.1 字符计数口径

长度校验统一用「去除空格与换行后的有效字符数」，**全系统只允许一套计数函数**，避免生成与校验口径不一致。

### 6.2 占位符检测

以下词命中即判 **FAIL**（除非有 `主体名称确认.json` 显式豁免）：`示例`、`XX`、`Demo`、`ACME`、`待用户确认`、`待补充`。

豁免要求：豁免文件中的取值必须与申请表当前值完全一致，否则豁免失效（防止改名后旧确认继续放行）。

### 6.3 商标核查

软件全称含品牌词/自造词/第三方平台名/®™ 时，须在**首次使用该名称之前**（即业务理解阶段之前）提醒用户二选一：
1. 去除商标文字（改纯描述性名称）
2. 保留原名并准备商标注册证复印件或权利声明

改名后，文件名、页眉、手册标题须全部重新生成。

```jsonc
// 输入

// 输出
```

```jsonc
  "checks": [{"id": "I-4", "level": "fail", "name": "页数一致性", "detail": "申请表写 60，实际渲染 62"}],
```

### 7.7 工具设计原则

1. **每步可独立调用**，不设黑盒 `kickoff`
2. **需要人工决策的点必须返回 `needs_user_confirmation: true`** 并停止
3. **脚本只做机械部分**，叙述性内容由调用方（agent）提供
4. **失败即失败**：不静默降级、不猜页数、不自动补全缺失输入

## 8. 验收标准

### 8.1 程序化检查（可自动化，须进 CI）

| # | 检查 | 判据 |
| --- | --- | --- |
| V-1 | 三份文件存在且非 0 字节 | 存在性 |
| V-2 | 命名一致性：申请表 vs 文件名 vs 页眉 | 全等 |
| V-3 | **页数一致性**：申请表「页数」vs PDF 页对象计数 | 全等（无 PDF 时降级为 docx 分页符计数） |
| V-4 | 占位符残留 | 黑名单 |
| V-5 | 编造/套话检测 | 可扩展黑名单 + 条件词判断 |
| V-6 | 截图尺寸不超限 | `IMAGE_MAX_WIDTH_IN`/`IMAGE_MAX_HEIGHT_IN` |
| V-7 | 申请表字段长度 | §6 约束表 |
| V-8 | 确认记录完整性 | 各确认文件存在且字段为真 |
| V-9 | 注释残留 | 复用剔除函数复检 |
| V-10 | 不变量 I-1~I-6 | 全通过 |

### 8.2 必须由**独立** agent/人工核实（程序无法判断）

| # | 检查 | 方法 |
| --- | --- | --- |
| H-1 | 代码真实性 | 随机抽 3–5 段回源文件逐行比对（**实际打开文件，不得凭"读起来像"**） |
| H-2 | 业务真实性 | 手册每句能否回溯到源码/README/视频帧 |
| H-3 | 截图匹配度 | **每张图单独打开核实**，不得批量假设 |
| H-4 | 行业/定位合理性 | 去掉项目名后信息量是否归零 |
| H-5 | 商标核查复检 | 按首次审查方式重审 |
| H-6 | 文风核实 | 是否机器生成特征（统一句式、万能套话） |
| H-7 | 设计取舍真实性 | 换成别的软件是否仍成立 |
| H-8 | 图注编号 | 章号/序号连续、无跳号重复 |
| H-9 | 自定章节 | 设立理由是否站得住 + 应设未设的缺口 |

> **强制独立性**：H-1~H-9 **必须**交由独立 agent，且委派时交付**原始问题**（"审计这份手册是否存在编造内容"），而非"验证此前生成的材料是否正确"（后者会诱导确认偏误）。

### 8.3 真实事故记录（须写入回归测试）

以下均来自 `S` 文档中记录的真实失败，**每条都应有对应的回归用例**：

1. 申请表页数取用**理论总页数**而非裁剪后实际渲染页数
2. 10 张截图依据记忆与并行调用返回顺序命名，**全部错位**
3. README 称"曲线在缺数据处断开"，实现是剔除该点连成连续折线
4. README 称报告"不含任何统计数字"，实际提示词保留了总评总分
5. README 称统计数值不外发，实际请求携带了时长、字数与问题词次数（**隐私声明失实**）
6. Python 文档字符串剔除后函数体为空，需 `pass` 补位
7. 操作手册目录是 Word 域，未更新即导出 PDF，页码全部印成 1（Word 中不显现，仅 PDF 可见）

## 9. 技术选型（已定稿）

> **决策：Python 单语言实现。** 依据见 §9.2。本节为定稿，改动须附新的决策记录。

### 9.1 定稿技术栈

| 层 | 选型 | 版本约束 | 理由 |
| --- | --- | --- | --- |
| MCP 框架 | `mcp`（官方 Python SDK） | Python **3.11+** | `@mcp.tool()` 由类型注解自动生成 JSON Schema，6 个工具零 schema 样板 |

| PDF 渲染 | `fpdf2`（**独立子进程调用**）+ `fontTools` | fpdf2 ≥ 2.8 | 精确控制分页；CJK 字体子集嵌入 |

| 包管理/分发 | `uv` / `uvx` | — | 用户无需预装环境，`uvx hag-mcp` 即可 |

**运行形态**：`uvx` 启动的 MCP server（stdio），不做单文件二进制。

### 9.2 选型决策记录

**候选对比（基于实际调研数据）**

3. **中文 PDF 链路已被验证**。`S/render_code_pdf.py` 已解决 CJK 字体探测、`.ttc` face 0 字重不对、字形覆盖校验等坑。
4. **PDF 是主输出**，该链路 Python 已跑通。

## 10. 已知陷阱清单（Checklist）

开发时逐项核对：

- [ ] 每页行数是 **50**，不是 55
- [ ] 渲染前断言 `50 × 15pt ≤ 756.9pt`，失败即报错
- [ ] 所有后端从**同一 IR** 渲染，逐页必须一致
- [ ] 页数取**渲染后回读值**，不是理论值、不是行数除法
- [ ] 折行在**抽取阶段**完成，"行"即最终物理行
- [ ] 注释剔除用状态机，Python 用 `tokenize`+`ast`
- [ ] 剔除后函数体为空时 `pass` 补位（并在清单中标注）
- [ ] PHP/Shell/Ruby/SQL/YAML/TOML 行尾注释残留 → WARN
- [ ] 切分点只在**完整文件边界**
- [ ] 偏差超 28–32 页即中止，不猜
- [ ] 软件全称/版本号在**文件名、页眉×2、申请表**四处全等
- [ ] 字符计数全系统**一套函数**
- [ ] `.docx` 目录是 Word 域，转 PDF 前必须更新域
- [ ] 手册正文由模型写，脚本不改写
- [ ] 截图逐张独立核实，不批量假设
- [ ] 独立验证 agent 用**原始问题**委派，不用"确认此物正确"
